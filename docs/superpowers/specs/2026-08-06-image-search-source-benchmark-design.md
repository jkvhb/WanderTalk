# 通用多源精准搜图能力对比试验设计

日期：2026-08-06  
状态：用户已确认原则，进入实施计划

## 1. 目的与产品边界

WanderTalk 的搜图能力不能绑定 318。未来无论输入 317、格聂南线、成都三日游或其他路线，系统都应使用同一套地点身份、来源选择、证据校验和失败处理能力。

本阶段先建立跨路线基准集和可重复执行的对比工具，不直接替换正式自动配图。试验要回答：

1. 不同图片来源对城市景点、偏远自然地标、道路节点和村落的覆盖能力；
2. 哪种来源组合能降低等待、失败和错图；
3. 哪些候选能证明属于目标地点，哪些只能待人工确认；
4. 哪些图片具备进入最终视频所需的来源与许可信息。

## 2. 最高优先级原则

### 2.1 地点身份先于视觉相似

图片必须先证明“它就是这个地点”，再判断画面是否美观、是否符合文案。桥、雪山、湖泊、寺庙等类别相同，不代表地点相同。

- “bridge、雪山、高原、lake”等类别词不能让候选通过地点身份校验；
- 视觉模型只能辅助检查画面内容，不能凭“看起来像”证明地点身份；
- 地点身份未通过时，视觉分再高也必须拒绝；
- 宁可标记“素材不足”，也不能用其他地点的同类图片补位。

例如金沙江大桥候选必须有证据指向竹巴笼、巴塘、芒康、G318 或对应坐标；伦敦塔桥等图片即使标签包含 bridge，也必须直接拒绝。

### 2.2 通用能力先于路线特例

不能为每条路线编写一套搜图规则。路线只提供节点资料，通用搜图内核按节点类型选择查询策略和来源：

- 城市地标：正式名称、行政区、官网或权威来源优先；
- 自然景观：正式名称、别名、行政区、邻近地标和坐标联合检索；
- 道路节点：坐标、道路编号和道路拓扑优先；
- 村落与观景点：名称、县域、附近景点和地理距离联合消歧；
- 同名地点：必须使用行政区或坐标排除错误地点。

## 3. 当前问题基线

当前流程由项目自行编排：AI 生成检索词，然后逐节点、逐检索词调用 Pixabay；未命中时再调用 Wikimedia Commons；选中后逐张下载、压缩并存入本地。

以 46 个节点、每点最多 4 个检索词、2 个来源计算，理论上最多会产生约 368 次搜索请求，且主要串行等待。Commons 网络不稳定；当前标签子串评分还可能把“同类事物”误判为“同一地点”。

## 5. 地点身份档案

所有来源使用同一份地点档案，避免不公平对比：

```text
canonicalName   正式名称
aliases         可信别名和常用叫法
adminPath       省、市、县等行政区
coordinates     已核验经纬度（如适用）
nearbyLandmarks 邻近地标
roadRefs        G318、G317 等道路编号（如适用）
nodeType        城市地标、自然景观、道路节点、村落或观景点
requiredTerms   能证明地点身份的词
negativeTerms   明确指向错误同名地点的词
visualTraits    身份通过后用于内容复核的可见特征
evidenceUrls    地点档案本身的核验来源
```

## 6. 多源适配结构

每个图片来源只负责把自己的响应转换成统一候选格式。通俗说：无论上游叫法如何，进入评分环节时都变成同一张“候选资料卡”。

候选资料至少包含标题、说明、标签、来源页、图片地址、作者、许可、经纬度、来源名称和请求耗时。

对比来源：

- **Pixabay + Commons**：当前基线；
- **Openverse**：开放许可媒体聚合来源；
- **Mapillary**：仅用于有坐标的道路、路口、垭口、服务区等地理节点；
- **Brave Image Search**：用于发现原始页面和补充地点证据，许可未知时不得自动入库。

缺少 Brave 或 Mapillary 凭据时，报告必须明确标记“未执行”，不能把人工网页搜索冒充 API 性能数据，也不能产生未确认费用。

## 7. 查询生成策略

查询由地点档案和节点类型确定，不依赖某条路线的专用代码：

1. 正式名称 + 县/市；
2. 可信别名 + 县/市；
3. 正式名称 + 邻近地标或道路编号；
4. 拼音/英文名 + 行政区；
5. 坐标附近搜索（来源支持且节点适用时）。

“川西高原”“雪山草原”等宽泛词不得用于具体节点自动配图，只能用于明确标注为“章节氛围”的另一类素材任务。

## 8. 两阶段判定

### 8.1 第一阶段：地点身份硬门槛

候选只能得到以下三种状态：

- `exact`：有足够证据证明是目标地点；
- `needs_review`：存在相关证据，但不足以自动使用；
- `rejected`：证据冲突、仅类别相似或明确属于其他地点。

具名地点自动通过至少需要：

- 正式名称或可信别名命中；并且
- 行政区、邻近地标、道路编号、坐标或可信来源页中至少一项一致；并且
- 未命中明确冲突的行政区、地点名称或负面词。

无正式名称道路节点不依赖文字名称，必须以坐标距离和道路编号/拓扑证明身份。

### 8.2 第二阶段：内容与许可评价

只有 `exact` 候选才继续评价：

- 视觉内容是否覆盖文案实际讲到的对象；
- 来源页是否可追溯；
- 作者、许可和署名要求是否完整；
- 清晰度、横竖构图和视频适配性。

最终自动入库还必须满足许可规则；地点准确但许可不明确的结果只能作为发现候选。

## 9. 性能与鲁棒性指标

每种方案记录：

- 首张 `exact` 图片出现时间；
- 每节点找到 3 张可用图片的时间；
- 请求总数、超时数、429/5xx 数量和重试次数；
- `exact`、`needs_review`、`rejected` 数量；
- 明显错图数，目标为 0；
- 无可靠结果节点数；
- 可直接用于视频与仅作发现候选的图片数；
- 缓存命中后再次执行的耗时。

## 10. 试验产物

输出逐节点、逐来源的表格报告，列出前三个候选、身份判定证据、许可状态、耗时和失败原因。只保存缩略图或来源链接，不写入用户当前行程，不覆盖已有素材。

报告给出：正式主来源、按节点类型启用的补充来源、暂不采用的来源，以及正式产品的并发数量、重试与缓存建议。

## 11. 后续正式改造方向

试验证明来源组合后，正式产品再实现：

- 3～5 个节点并行处理（不再逐个排队）；
- 检索词和来源响应缓存；
- 短暂网络错误延迟重试；
- 连续失败来源自动暂时停用（避免拖累整批）；
- 先做身份和质量判断，后下载最终图片；
- 成功、部分成功、素材不足、待确认和来源故障分别显示；
- 新路线只增加地点数据，不增加路线专用判断代码。

## 12. 验收标准

- 20 个跨路线节点都有可复核记录；
- 当前方案与至少一个新来源完成相同条件对比；
- “同类但不同地点”的图片不能成为 `exact`；
- 金沙江大桥测试必须拒绝伦敦桥等负例；
- 明显错图自动入选数为 0；
- 无结果时返回素材不足，不使用宽泛图片补位；
- 版权未知候选不得标为可直接使用；
- 所有结论能追溯到请求结果或原始来源页；
- 不修改现有行程、节点图片和视频素材；
- 不提供新接口凭据时不得产生费用。
